## Project Purpose

COBRA (A Circuit-Level Open-Source Based RFIC AI-Assisted Optimizer) is a 
Python framework that combines circuit simulation through Xyce with surrogate 
component models (generated by ORCA), optimization algorithms, and optional 
electromagnetic fine-tuning using AWS Palace to optimize circuit designs.

## Repository Structure

- `src/cobra/cobra.py`: top-level optimization orchestration.
- `src/cobra/__main__.py`: `cobra` CLI and GUI entry point.
- `src/cobra/configuration/`: run-configuration schema, config-driven runs, geometry loading, and component settings.
- `src/cobra/optimizers/`: optimization properties, goals, and optimizers.
- `src/cobra/spice_sim/`: Xyce, netlist parsing, results, and HB analysis.
- `src/cobra/stages/`: surrogate, simulation, optimization, and fine-tuning stages.
- `src/cobra/gui/`: PySide6 windows, dialogs, workers, and plots.
- `docs/`: user and API documentation.
- `examples/`: usage examples.

Find the owner of a behavior before editing. Keep parsing, configuration,
simulation, optimization, GUI, and orchestration logic in their existing modules.

## General Rules
- Delegate to a subagent in `.claude/agents/` only when it pays: to move work
  onto a cheaper model (`cobra-documentation-agent`, `cobra-linting-agent`), to
  keep noisy tool output out of this context, to get a fresh-context review
  (`cobra-reviewing-agent`), or to run independent changes in parallel. A single
  edit you can already make is cheaper to do directly than to delegate — a
  subagent starts cold and re-derives context you already have.


### 1. Think Before Coding

**Don't assume. Don't hide confusion. Surface tradeoffs.**

Before implementing:
- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them - don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

### 2. Simplicity First

**Minimum code that solves the problem. Nothing speculative.**

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it.

Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

### 3. Surgical Changes

**Touch only what you must. Clean up only your own mess.**

When editing existing code:
- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it - don't delete it.

When your changes create orphans:
- Remove imports/variables/functions that YOUR changes made unused.
- Don't remove pre-existing dead code unless asked.

The test: Every changed line should trace directly to the user's request.

### 4. Goal-Driven Execution

**Define success criteria. Loop until verified.**

Transform tasks into verifiable goals:
- "Add validation" → "Write tests for invalid inputs, then make them pass"
- "Fix the bug" → "Write a test that reproduces it, then make it pass"
- "Refactor X" → "Ensure tests pass before and after"

For multi-step tasks, state a brief plan:
```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
```

Strong success criteria let you loop independently. Weak criteria ("make it work") require constant clarification.

## Python

- Use UV to manage the repository environment at the base directory: `.venv/`.
  Run `uv sync` after dependency or lock-file changes; it creates or updates
  `.venv/` from the project metadata. Use `uv run <command>` for commands that
  should run in the project environment, or prefer `.venv/bin/python`,
  `.venv/bin/pytest`, and `.venv/bin/cobra` when an explicit executable path is
  useful. If the environment must be created manually, use `uv venv --python
  3.11` before syncing. Do not silently use a global interpreter. Fall back to normal virtual environments, conda, or system Python only when uv is unavailable or the user explicitly requests it.
- Follow the existing type-hint, dataclass, naming, formatting, and import style.
  Use clear names and keep functions focused.
- Prefer object-oriented design that matches the existing abstractions. Extend
  the relevant base class or stage when behavior belongs to an existing
  lifecycle; do not add parallel utility APIs without a clear need.
- Keep classes cohesive, dependencies explicit, and public methods small enough
  to test. Avoid hidden global state, mutable defaults, and one-letter names.
- Validate inputs at boundaries and use existing errors, especially
  `ConfigurationError`, with actionable messages.
- After implementing or modifying Python files, run `ruff check path/to/file.py`
  and `ty check path/to/file.py`. Fix relevant findings before finishing.

## CLI and Configuration

- Preserve the `cobra` entry point and `cobra run CONFIG` command.
- Reject unknown fields, bad schema versions, missing files, invalid links, and
  invalid goals before simulation starts.
- Resolve relative netlist, model, and custom geometry paths relative to the
  config file, matching `RunConfiguration.load()`.
- Update `docs/user-guide/configuration.md` when the schema changes.
- Test valid and invalid configs, including path and error cases.

## Simulation and Optimization

- Xyce may be provided by Spack. In that case, load it before running COBRA:

  ```bash
  . ../spack/share/spack/setup-env.sh && spack load xyce
  ```

  Keep this setup in the same shell as the COBRA command and verify Xyce with
  `command -v Xyce` and `Xyce --version`.
- Do not run Xyce, Palace, or long Optuna jobs in the foreground.
